# 要件定義書: ランチルーレット

## 1. 概要

会社などで昼食のメニューに迷ったときに、候補の中からランダムに1つを選んでくれる
Webアプリケーション。ブラウザ上で完結する単体のWebアプリとして提供する。

出典: `human_input.md`（変更しない一次情報）

## 2. 目的

- 昼食の候補選びに迷う手間をなくし、ランダムに1つを決定できるようにする
- 勉強会でのデモ利用を想定し、見た目にも配慮した「ちょっとしたWebサービス」らしい仕上がりにする

## 3. スコープ

### 3.1 対象とする

- ブラウザ単体で動作するWebアプリ（HTML/CSS/JavaScriptのみ）
- ランチ候補の管理（初期候補・追加・削除）
- ルーレットによるランダム選出とその視覚的演出
- ロジック部分の自動テスト（Vitest）

### 3.2 対象外とする

- サーバーサイド処理、外部API連携
- データベースへの永続化
- ログイン・ユーザー管理
- 画面を閉じた後の状態保存（永続化）
- React/Vue等のフロントエンドフレームワーク
- Canvasを用いた描画
- 外部UIライブラリの利用

## 4. 機能要件

### 4.1 候補管理

| ID | 内容 |
|----|------|
| F-1 | 初期候補として以下の6件を表示する: 🍜ラーメン, 🍛カレー, 🍣寿司, 🍝パスタ, 🍱定食, 🍲うどん |
| F-2 | 画面上の操作で候補を追加できる |
| F-3 | 画面上の操作で候補を削除できる |
| F-4 | 候補が2件のときは、それ以上削除できない（常に2件以上を維持する） |
| F-5 | 候補データはブラウザを閉じるまでの間のみ保持されればよく、永続化は不要 |

### 4.2 ルーレット

| ID | 内容 |
|----|------|
| F-6 | 画面の主要な要素として、円形のルーレットを表示する |
| F-7 | ルーレットの各セクションは候補ごとに色分けされ、本物のルーレットのような見た目にする |
| F-8 | ルーレット上部付近に、停止位置（選ばれた候補）を示す矢印（ポインター）を表示する |
| F-9 | ルーレット中央に「SPIN!」ボタンを配置する |
| F-10 | SPINボタン押下でルーレットが回転を開始し、勢いよく回った後、2〜3秒程度かけて徐々に減速して停止する |
| F-11 | 候補からランダムに1件を選出できる |
| F-12 | 選ばれた候補とルーレットの実際の停止位置（矢印が指す候補）が常に一致する（矛盾しない） |

### 4.3 結果表示

| ID | 内容 |
|----|------|
| F-13 | 回転停止後、選ばれた候補を大きく表示する（例: 「🎉 今日のランチは / 🍣 寿司！」） |

## 5. UI/UXデザイン要件

見た目は勉強会でのデモに使うため重視する。「いかにもサンプルHTML」ではなく、
実際のWebサービスに近い仕上がりを目指す。ただし、見た目のために構成を複雑にはしない。

| ID | 内容 |
|----|------|
| D-1 | 全体のトーンは明るく楽しい雰囲気にする |
| D-2 | 背景は薄いオレンジ〜ピンク系のグラデーションにする |
| D-3 | コンテンツは白いカードとして表示する |
| D-4 | カードや要素の角は丸くする |
| D-5 | 適度な影（シャドウ）をつける |
| D-6 | ルーレットの各セクションはパステル系の複数色を使う |
| D-7 | SPINボタンは目立つ色にする |
| D-8 | 文字は読みやすいこと |
| D-9 | 絵文字を活用する |

## 6. レイアウト・レスポンシブ要件

| ID | 内容 |
|----|------|
| L-1 | PC幅では、左側にランチ候補一覧、右側に大きなルーレットを配置する |
| L-2 | スマートフォンでも閲覧可能とし、画面幅が狭い場合は縦並びのレイアウトに切り替える |

## 7. アニメーション・演出要件

| ID | 内容 |
|----|------|
| A-1 | ルーレットの回転は視覚的に自然なアニメーションとして表現する |
| A-2 | 結果表示時、少し拡大するなどの演出を加える |
| A-3 | ボタンや候補削除などの操作要素は、マウスホバー時に軽い反応（見た目の変化）を示す |

## 8. 技術要件

| ID | 内容 |
|----|------|
| T-1 | HTML / CSS / JavaScriptのみで実装する（フレームワーク不使用） |
| T-2 | ルーレットの描画にCanvasは使用しない。通常のHTML/CSSでシンプルに実現する |
| T-3 | 外部API、DB、外部UIライブラリは使用しない |
| T-4 | ロジック部分は自動テスト可能な形にする |
| T-5 | テストフレームワークにはVitestを用いる |

## 9. テスト要件

以下の観点を自動テストで確認する。

| ID | 内容 | 対応する機能要件 |
|----|------|----------------|
| TC-1 | 候補から1件をランダムに選べること | F-11 |
| TC-2 | 候補の追加ができること | F-2 |
| TC-3 | 候補の削除ができること | F-3 |
| TC-4 | 候補が2件未満になる削除はできないこと | F-4 |
| TC-5 | 選ばれた候補とルーレットの停止位置が矛盾しないこと | F-12 |

## 10. 非機能・前提事項

- 小規模なアプリであり、必要以上に複雑な構成にはしない
- 要件・設計・実装・テストの一貫性を保ち、一通りの成果物を残す
- `human_input.md` は一次情報として変更しない
